projects / finora

finora — personal expense tracker

a quiet place to log what comes in and what goes out, set a monthly and a weekly budget, and see the whole month honestly.

plain htmlcssjavascriptsupabasepostgresqlrow level securitychart.js

the brief

Build a personal expense tracker that is simple enough to explain in a minute and complete enough for everyday use: real accounts with email confirmation and password recovery, income and expense entries, a monthly summary, monthly and weekly budgets, filters, and a category breakdown.

The constraints mattered as much as the features: plain HTML, CSS, and ES modules; no framework, no build step, and no runtime CDN (Chart.js is vendored locally); plus a Supabase publishable key in the browser with Row Level Security doing the real access control.

the approach

Finora lives in its own repository as a static shell plus eleven small ES modules. app.js chooses between the auth screen and the dashboard, dashboard.js owns one month of state alongside the current ISO week, and supabase-store.js wraps GoTrue and PostgREST behind a small store interface.

Sample-data mode was deliberately removed so the app is real accounts only — one store, one data path, and zero drift between mock state and Postgres. Request tokens guard month navigation so a slow response never overwrites a newly selected month.

accounts and budgets

Supabase Auth handles email/password sign-up, confirmation links, sign-in, and a non-enumerating forgot-password flow that saves a new password through PUT /auth/v1/user and opens the dashboard directly.

Entries and limits live in two Postgres tables: transactions uses numeric(12,2) amounts and real date values, while budgets keys on (user_id, period, period_start) to support both monthly budgets and Monday–Sunday ISO weekly budgets.

security

Each table enforces four owner-only policies comparing (select auth.uid()) = user_id, anon holds zero table privileges, and default TRUNCATE grants (which bypass RLS in Postgres) are explicitly revoked from both anon and authenticated.

I verified this against the live database with two impersonated users: each saw only their own rows, cross-user updates and deletes affected zero rows, a forged user_id insert failed with 42501, and anon was denied. Test accounts and rows were cleaned up afterwards.

monochrome single-column design

The dashboard reads top to bottom in one column capped at 760px: month bar → three summary numbers (In, Out, Left) → monthly and weekly budget meters → entries → a collapsed native <details> panel for the category doughnut and daily insights.

The palette is strictly black ink on white paper with a ten-step grey ramp. Meaning rides on weight, sign, and shape instead of colour: bold + for income, regular − for expenses, grey fill near a budget limit, and black diagonal hatching past it.

phone layout and accessibility

Fluid clamp() sizing and a six-tier phone breakpoint ladder down to 320px turn table rows into bordered cards with 44×44px touch targets, dock dialogs to the bottom as sheets, and respect device safe-area-inset-* margins.

Every field keeps a visible label and aria-describedby alert errors, native <dialog> handles focus trapping and Escape, and a text legend repeats every category value beside the decorative canvas. Four axe-core runs across auth, recovery, and the dashboard reported zero WCAG A/AA violations.

testing and deployment

Twelve dependency-free node --test unit tests cover money formatting, date boundaries, and ISO week maths, backed by 41 jsdom integration checks across the dashboard, budget meters, and password-recovery flows.

GitHub Actions runs the unit suite before deploying every push to GitHub Pages, and vercel.json ships clean URLs and security headers with zero build step.

what i’d add next

CSV export, recurring entries, custom SMTP to lift Supabase’s default email rate ceiling, and user-defined categories stored per account. Each is a real improvement, while keeping the core loop small and readable.
