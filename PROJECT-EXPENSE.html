projects / ledger

ledger — personal expense tracker

a quiet place to log what comes in and what goes out, set a monthly budget, and see the whole month honestly.

plain htmlcssjavascriptsupabasepostgresqlrow level securitychart.js

the brief

Build a personal expense tracker that is simple enough to explain in a minute and complete enough to be useful: accounts, income and expense entries, a monthly summary, one budget, filters, a category chart — and a way for visitors to try it without typing real financial information.

The constraints mattered as much as the features: plain HTML, CSS and JavaScript; no React, no build step; separate files; and a Supabase publishable key in the browser with Row Level Security doing the real work.

the approach

The app is a static shell plus eleven small ES modules. app.js decides between the auth screen and the dashboard, dashboard.js owns one month of state, and a tiny store interface has two implementations: Supabase for real accounts and localStorage for demo mode.

That seam is the main design decision. The demo is not a separate mock screen — it runs the same filters, dialogs, stats, chart and validation as the real app. It also meant the UI could be tested thoroughly without a database.

accounts and data

Supabase Auth handles email/password sign-up, login, logout and confirmation links. Transactions and budgets live in two Postgres tables; money is numeric(12,2), dates are real date values, and a user has at most one budget per month.

Every transaction is owned by auth.uid() through a default plus a foreign key to auth.users. The frontend never filters by user id in its queries — policies on the table do that, so a manipulated request cannot widen its own access.

security

Each table has four owner-only policies and the anon role has no table privileges at all. Only the publishable key ships; no service-role key exists anywhere in the folder.

I verified this in the live database with two impersonated users: each saw only their own rows, cross-user updates and deletes affected zero rows, a forged user_id insert was rejected with 42501, and anon was denied. The temporary users and rows were deleted afterwards.

the demo

The demo seeds a current month clipped to today, a previous month with a budget, and a month before that without one. Everything is editable, the state survives a refresh in that browser, and Reset sample data restores the seed.

It never calls Supabase and never uploads anything. The tradeoff is honest: it is local sample data for exploring the interface, not private storage.

design and accessibility

The interface uses one warm neutral palette, a mono micro-label system, and a single accent for action. On mobile the table becomes labelled cards rather than shrinking into unreadable columns; the chart legend carries the category values so the canvas is never the only source of information.

Forms keep visible labels, link errors with aria-describedby, and announce them; native <dialog> provides the focus trap and Escape handling; the theme respects the system preference and remembers the choice. An axe-core pass in Chromium found no WCAG A/AA violations across the auth screen, dashboard, empty month and entry dialog, in light and dark themes.

testing

Fifteen dependency-free unit tests cover formatting and the demo store, including persistence failures and rollback. During development I also ran 14 jsdom UI-flow checks and 40 real-Chromium checks covering add/edit/delete, reload persistence, budgets, filters, empty states, validation, focus return, dark mode and mobile layout.

The one thing automated checks cannot prove here is the full email-confirmation round trip; that is a browser step after deployment, and it is listed in the README checklist.

what i’d add next

CSV export, recurring entries, a password-reset screen, and user-defined categories stored per account. Each is a real improvement, but none of them is needed to make the core loop feel finished — and keeping that loop small is why the app is easy to read.
